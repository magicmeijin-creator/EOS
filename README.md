# EOS 智慧補貨與稽核系統（前後端示範）

## 功能

- 門市補貨：可切換多間示範門市，一次盤點多個商品並建立補貨單。
- 建議量：依每項商品近 7 日逐日銷售計算日均需求；店長輸入當日實際盤點量後，系統即時更新再訂購點與建議補貨量。
- 防呆：補貨量與建議差異過大時，顯示提醒並要求填寫原因；門市仍可提出特殊需求，不會只因數量可疑就直接刪除。
- 店長確認：勾選確認後送交總部；未勾選則進入「待店長確認」，不會立即送出或送倉。
- 逾時處理：待確認 10 分鐘後，系統將手動修改量改回各商品的建議量，送交總部審核，並留下稽核紀錄；總部核准前不會標記為送倉。
- 總部審核：可核准店長申請量、改採系統建議量、退回門市重新確認或暫緩處理。退回後門市可調整各項補貨量與原因，再重新確認；暫緩單仍可繼續審核。
- 責任稽核：保留門市確認、逾時、主管決策及聯絡狀態的操作時間軸。

## 執行方式

1. 安裝 Node.js 18 或更新版本。
2. 在此資料夾執行 `npm install`。
3. 執行 `npm start`。
4. 開啟 `http://localhost:3000`。

## 倉儲庫存基礎串接

- EOS 會透過 `WMS_API_URL` 讀取倉儲系統的 `/api/inventory`，預設為 `http://127.0.0.1:3001`。
- EOS 的「統家便利商店」會讀取倉儲系統 `/api/products` 的商品清單，商品代碼直接使用 `product_code`；中央倉各批可供數量顯示在商品卡片。
- 兩個系統都在同一台電腦執行時，請讓倉儲系統使用 3001 埠、EOS 使用 3000 埠。可在啟動倉儲系統前於 PowerShell 設定 `$env:PORT=3001`；另一個 PowerShell 視窗再啟動 EOS。
- 若倉儲系統使用 3002，啟動 EOS 前設定 `$env:WMS_API_URL="http://127.0.0.1:3002"`。
- 竹南門市的盤點庫存由 WMS 現有可用庫存預填；近 7 日已完成出貨量也由 WMS 自動預填到可編輯欄位。兩項預設值在 WMS 與 EOS 相同，使用者都可核對後調整。交期預設 1 天，安全庫存參考商品最低庫存設定，請依實際營運再調整。
- 補貨建議量與申請量使用整數；若門市盤點庫存含小數，系統會將建議申請量向上取整，避免建議量低估。
- 總部核准補貨單時，EOS 會按入庫先後分配中央倉批次，呼叫倉儲出貨 API 建立待揀貨單。倉管在倉儲系統「出貨單」完成揀貨出貨後，門市可回 EOS 確認收貨，更新該門市庫存。
- 統家便利商店可直接從 WMS 左側「補貨申請」送出需求；EOS 總部會在「總部訂單審核」收到補貨單。EOS「中央倉出貨管理」集中列出 WMS 出貨單，可按門市、出貨狀態與訂單／商品關鍵字篩選。
- 倉儲庫存與商品清單來自 MySQL；EOS 門市資料、補貨單及門市盤點數量目前仍存於 Node.js 記憶體，重啟 EOS 會清空。正式使用前需改成持久化資料庫並補上帳號／角色控管。

## 補貨計算

- 日均需求 = 近 7 日每日銷售量的平均。
- 再訂購點 = 日均需求 × 供貨前置時間 + 安全庫存。
- 目標庫存 = 日均需求 ×（供貨前置時間 + 檢視頻率）+ 安全庫存 + 額外緩衝量。
- 建議補貨量 = max(0, 目標庫存 − 當日盤點庫存)。

## 示範資料

系統內建中壢中原、台南永康、台北信義三間示範門市，每間各有輕便雨衣、瓶裝水及鮮奶吐司等商品。銷售紀錄、盤點數量、交期與安全庫存皆為示範值，並非真實門市資料。

## 正式上線前的重要事項

1. 訂單與門市商品資料目前存於 Node.js 記憶體，伺服器重啟會清空；逾時處理也只會在伺服器持續執行時運作。正式系統應改用資料庫並使用可持續執行的排程機制。
2. 目前近 7 日銷售和盤點值為示範資料／手動輸入；正式上線需串接 EOS 銷售、每日盤點、在途訂單與供應交期資料，並依商品特性校準安全庫存及公式。
3. 聯絡功能僅建立稽核紀錄，不會真的傳送簡訊、LINE WORKS 或 Push 通知；正式串接需使用核准的通知服務/API。
4. 正式部署應加入帳號登入、角色權限、CSRF/輸入驗證、HTTPS、操作紀錄保存、備份與個資存取控管。
5. 異常門檻目前是示範規則：申請量超過 max(建議量 × 3, 建議量 + 50 個商品單位) 時，標示需確認並要求填寫原因；門市仍可提出特殊需求。此門檻需由營運單位依商品特性調整。
